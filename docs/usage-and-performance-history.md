# Permanent usage and performance history

## What is counted

No volume limits or billing enforcement are enabled. Namespace/child reservation quotas are unchanged.
The dashboard Traffic history panel and authenticated `GET /api/v1/usage?month=YYYY-MM`
return account totals, namespace totals including children, individual host totals and UTC daily counts.
The web session endpoint is `GET /api/usage?month=YYYY-MM`; both derive the owner from authentication,
never from a caller-supplied user ID. Responses are private and uncached.

- Every request reaching the control plane for a registered public endpoint counts once on arrival,
  including HEAD, errors, offline tunnels, cancellations and WebSocket upgrade attempts.
- Successful public WebSocket upgrades also increment `websocketConnections` at acceptance.
  Frames and the agent's internal control socket do not count as new connections.
- Raw TCP/TLS endpoints are not implemented in Bore. `tcpTlsConnections` is **null/unsupported**,
  not a fake zero or a count of HTTPS transport connections. The database reserves a counter for future support.
- Signed internal probes and prewarm requests increment `syntheticRequests`, not `httpRequests`.
  Their timings use separate `probe:http` cohorts. Other bots and customer health checks count normally.
- Platform login/API traffic, unknown hosts and traffic rejected at Traefik before the control plane are excluded.

All monthly/daily boundaries are UTC. An HTTP request belongs to its arrival day; a successful WebSocket
connection belongs to its acceptance day. Owners and reservation/child IDs are frozen on arrival, so a
namespace changing owners mid-request does not move its traffic to the new owner.
Coverage starts at `trackingSince`; the first month is partial. Historical request totals cannot be reconstructed
reliably from resettable IP counters or older unsplit probe traffic, so they are not invented/backfilled.

## Storage and durability

PostgreSQL `monitoring.usage_counts` holds one leaf counter per owner/reservation/child and UTC day, month,
or lifetime. Account and parent namespace totals sum leaves exactly once. No IPs, URLs or per-request rows
are stored here. Indexed monthly/lifetime queries do not scan the complete daily history.
Rows have no cascading foreign keys and are never pruned by normal operations: releasing a namespace,
removing a child, resetting IP statistics, or deleting an account does not delete historical volume.
A reused hostname has a new reservation ID and remains a separate historical cohort.
Account erasure/privacy obligations, if required, need an explicit history-erasure workflow.

Requests update bounded in-memory aggregates, not PostgreSQL individually. Endpoint ownership is indexed by
cached metadata revision: no additional database lookup or full state copy per request. Every approximately
15 seconds, a transaction writes the batch and its daily/monthly/lifetime rollups. A writer UUID plus sequence watermark
makes retries after an ambiguous commit idempotent. Watermarks retain one row per process start, not per flush.
Failed batches are retained and retried while the process lives; shutdown drains outstanding buffers.
There are at most 4096 new usage scopes plus one pending bounded batch. Overflow increments `droppedUsage`;
raw performance buffers report `droppedMetrics`. Unexpected termination can lose unflushed data, and sustained
database outages can overflow buffers. This is operational monitoring, **not a crash-proof billing ledger**.
Drop counters, missing samples and process restarts must be considered when evaluating coverage.

Probe signatures use a dedicated secret generated by `scripts/configure-postgres.sh`, HMAC-bound to host,
method and a two-minute timestamp window. Spoofed unsigned headers do not bypass counting. The header is
removed before forwarding to customer applications. Production requires the secret file; fixture mode can omit it.

## Permanent bottleneck history

Recent request-minute buckets, 15-second runtime samples, minute probes and device events remain available
for 14 days. Hourly compaction first converts older data to UTC daily `monitoring.daily_metrics`, then deletes
raw rows **in the same PostgreSQL transaction**. Compactors serialize with an advisory lock. Failed compaction
rolls back both archival and deletion; repeated compaction and late data do not double-count.
Daily summaries have **no automatic expiration**:

- Requests: counts by host/protocol/outcome/status, summed latency/routing/relay/local timing,
  local-timing coverage, response bytes, maximum duration, and merged latency histograms.
- Probes: host/status/error/expected-connected cohorts; count, mean, minimum and maximum DNS,
  connection, TLS, first-byte and total timings. Probe stage timings are cumulative from request start.
- Runtime/host: numeric allowlisted CPU, memory, event-loop, queue, buffered-byte, device RTT,
  drops, load, swap, metadata size and namespace/connection samples, with count/sum/min/max.
- Device events: permanent connection/disconnection/error category counts by device and close code.

Request averages are weighted by request counts; local timing averages use local-timing counts.
p95 is a histogram upper-bound estimate, not an average of percentiles. The last bucket is `>30000ms`.
The maximum runtime `eventLoopP99Ms` is the worst sampled p99, not a whole-day percentile.
Older individual requests, sample chronology, exact stack traces and arbitrary textual Docker logs are **not**
retained forever. Permanent structured summaries allow historical comparisons without per-event storage.
Data that was pruned before this feature cannot be recovered. Existing retained samples are labeled `legacy`.

Deploy with `sh scripts/deploy-production.sh` from clean, pushed, aligned `master`. The script injects the
exact Git revision into monitoring. Release first-seen timestamps are retained in `monitoring.releases`.
Raw request/device buckets spanning two revisions within the same minute are explicitly labeled `mixed`;
manual deployments without the revision environment variable are `unversioned`, never falsely attributed.

## Inspect production

Reuse a single SSH shell; execute commands sequentially in `/srv/bore/repo`.

```sh
# Recent detailed diagnosis: last 6 hours, optionally one host.
docker compose --env-file .env.production -f compose.control-plane.yml exec -T monitoring node apps/control-plane/dist/src/monitoring/report.js 6 eva.bore.dk

# Forever daily history: inclusive UTC dates, optional host.
docker compose --env-file .env.production -f compose.control-plane.yml exec -T monitoring node apps/control-plane/dist/src/monitoring/history-report.js 2026-01-01 2026-12-31 eva.bore.dk

# All accounts: month/lifetime totals, namespaces, children, daily volume.
docker compose --env-file .env.production -f compose.control-plane.yml exec -T monitoring node apps/control-plane/dist/src/monitoring/usage-report.js

# One account and historical month.
docker compose --env-file .env.production -f compose.control-plane.yml exec -T monitoring node apps/control-plane/dist/src/monitoring/usage-report.js user@example.com 2026-10
```

The long-range report combines raw and archived tiers in a single consistent SQL snapshot, returning daily
revision/category/cohort metrics and release markers. Compare equivalent weekdays/traffic levels and
request outcomes across revisions; improved means with changed workloads alone do not establish causality.
Use probe `expectedConnected=true` to distinguish actual outages from deliberately disconnected tunnels.

Storage grows with active endpoint-days/category combinations and sampled device-days, not visitors or
individual requests. Forever retention still requires capacity planning. Inspect sizes with
`SELECT relname,pg_size_pretty(pg_total_relation_size(relid)) FROM pg_catalog.pg_statio_user_tables
WHERE schemaname='monitoring' ORDER BY pg_total_relation_size(relid) DESC;`.
Normal PostgreSQL backups include the permanent tables. Backups retained for 14 days do not mean live
history expires; off-server backups are still required for protection against VPS/disk loss.

## Verification

Run `TEST_DATABASE_URL=... pnpm test`, `pnpm typecheck`, and `pnpm build` with a disposable PostgreSQL server.
The archival tests create an isolated database and therefore need CREATE DATABASE on that test-only role.
They cover rollback on failed compaction, retries, late arrival, weighted summaries, permanent retention,
owner isolation, child rollups, release/reuse, calendar validation and signed-probe exclusion.
For browser smoke checks, start the built web app locally against that test database, then run
`TEST_DATABASE_URL=... BORE_TEST_CHROME=/path/to/chrome pnpm exec node scripts/verify-usage-dashboard.mjs`.
The default web origin is `http://localhost:3307` (override with `BORE_TEST_WEB_ORIGIN`). This creates and
cleans a test account, meters 10,000 requests, checks authenticated desktop/mobile rendering and page overflow,
and produces screenshots in the system temporary directory. Never point this check at a production database.

Implementation relies on PostgreSQL's [JSON recordset functions](https://www.postgresql.org/docs/18/functions-json.html)
and [data-modifying CTE RETURNING semantics](https://www.postgresql.org/docs/18/queries-with.html) for batched rollups and atomic archival.
